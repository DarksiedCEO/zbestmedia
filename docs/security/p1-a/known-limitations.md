# P1-A Known Limitations

- This package is a threat-model and validation contract, not a runtime control implementation or production certification.
- Live configuration, deployed SHA, network policy, branch protection, provider retention, database RLS, backups and secret custody remain unproven.
- Three founder decisions—tenant/workspace authority, production credential custody, and outbound data/egress policy—remain unresolved for implementation and block P1-B.
- `pnpm prisma:generate:all` was observed locally failing while invoking `pnpm -C services/brandgraph prisma generate --schema prisma/schema.prisma` with `Command "services/brandgraph" not found`. The defect is outside P1-A, does not alter this package’s model validation, and is assigned to the repository build-tool owner for a separately authorized package. It was not remediated here. Full-workspace validation must not be described as locally GREEN on the strength of that command.
- Runtime failure injection, cross-tenant denial, SSRF destructive testing, rollback rehearsal, Sentinel operation, tamper-evident evidence custody, credential rotation and production recovery are deferred to their authorized P1 packages and remain NOT_PROVEN.
- **Cross-repository CI authentication is NOT_PROVEN.** The `evidence_binding` control resolves runtime-pin evidence against the private `DarksiedCEO/zbestmedia-ui` object store via a read-only isolated query. CI running in `DarksiedCEO/zbestmedia` cannot read that private repository with the default `GITHUB_TOKEN`. Runtime-pin evidence binding is therefore `NOT_VERIFIED` in CI (which blocks, never passes) until a founder-provisioned scoped GitHub App token or read-only deploy key is supplied. Local runs prove it by passing `--runtime-git-dir` against an authenticated isolated mirror.
- **The external trust anchor must be supplied out-of-band.** `authorizedBaseSha` and `runtimeEvidenceSha` in this candidate are candidate-controlled and are NOT self-trusting. The `trust_anchor` control requires the anchor via `--base-sha`/`--runtime-pin` (operator) or CI secret; absent anchor is `NOT_VERIFIED` and blocks. This is what defeats coordinated SHA substitution to an alternate runtime commit.
- The runtime isolated mirror is a local read-only artifact and is not present in the CI workspace; its provisioning in CI is part of the same founder credential decision above.
- **External trust-anchor custody is itself a trust boundary.** The `P1A_TRUST_BASE_SHA` / `P1A_TRUST_RUNTIME_PIN` repository variables must be writable only by repository admins (not by any workflow, `GITHUB_TOKEN`, or PR author), and every change to them must be audited. By design a changed anchor produces a candidate/anchor mismatch and BLOCKS — i.e. altering the anchor invalidates certification for the exact SHA it certified. The anchor is only as trustworthy as its custody; that custody is a founder/repo-admin control, not a candidate control.
- **P1-A CI uses a bounded single-job cross-repo check; the hardened trusted-branch certifier (independent judge, credential-isolated acquisition, durable evidence bundles) is deferred to P1-H.** The residual — the candidate validator runs in the job that mints the read-only runtime token — is accepted as a documented, time-boxed limitation for P1-A closure, mitigated by a read-only single-repo short-lived auto-revoked token, and is scheduled to be superseded by the P1-H certification package.
- **Path safety is enforced structurally, not by blob-absence.** `assertSafeRepoPath` rejects absolute/drive paths, `..`/`.` segments, backslashes, NUL, non-ASCII/control characters (unicode slash lookalikes), and percent-encoded sequences (`%2e`/`%2f`/`%5c` and double-encoded `%25xx`) before any object query — so a repository that happened to contain a literal encoded filename cannot create ambiguous accept/reject behavior.
